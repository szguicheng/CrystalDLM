# AR → Diffusion 重试切换诊断

## 已确认的原因与边界

失败发生在 AR 没有发出 `<CRYSTAL_START>`，此时 Diffusion 尚未被执行。原始首轮 70/70 都能自然切换，但反馈重试只有 5/122 能切换。不能把其余 117 次直接解释成 Diffusion 结构修复失败。

实际训练样本只有 `生成请求 → 说明 → START → 晶体 → END`，以及随后读取结构事实的 Q 问答；没有训练 `晶体 → 错误反馈 → 第二次生成`。旧重试程序却直接采用后一种多轮输入。这是训练使用的任务格式与运行输入之间的差异。

对固定14个失败上下文，匹配纯AR检查点和FLARE检查点都得到0/14自然START；延长文字上限至768后分别为0/14和1/14。重复原始生成指令、简化反馈、补EOS分隔也均为0/14。因此证据不支持“共享AR/Diffusion参数必然导致不能切换”，也不支持把256-token上限作为主要原因。

旧控制token/time embedding扫描与训练一致；已验证新旧单段去噪logits一致。只是删去历史晶体标记恢复2/14，未达到完整修复。真正恢复14/14自然START的是：以原始生成要求开始一个新请求，把失败晶体和原检查结果放入该请求的数据区，最后使用标准Assistant生成入口。

最后的上下文重组同时改变了对话角色组织和旧解释文本的保留方式；本轮不把其中某一个词或分隔符单独宣称为唯一原因。证据支持的是旧多轮输入契约不适合当前训练方式，而新生成请求契约恢复了切换。

## 修复内容

`context.py`保留原始空间群和ehull要求，保留上一轮实际晶体文本及检查反馈；将旧晶体的控制标记作为传输边界移除，数据正文作为当前请求的输入。当上一轮根本没有晶体时，保留其失败的AR响应作为数据。该函数不会在新输出前补START，模型仍需自己生成START才能进入Diffusion。

没有修改模型权重、采样种子、温度、256-token文字上限、544-token晶体上限、Diffusion实现或结构成功标准。没有训练新的模型。旧runner和旧结果保留，修复使用独立入口 `switch_fix/run.py`。

## 验证

两个上下文回归测试通过；实际tokenizer下，修复函数产生的14条输入token与成功探针完全一致，输入中没有START标记。完整验证保持70组初始候选及直接重试对照不变，仅重新生成修复后的反馈尝试；14个诊断组与其余56组单独报告。完整输出位于 `switch_fix/run_001/`。

探针原始记录见 `../switch_diagnosis/{flare,ar,context_probe}/`，完整协议和探针对照表见 [PROTOCOL.md](PROTOCOL.md)。GRACE与训练均未参与本轮修复。

完整复验已结束：122/122自然切换，新增有效晶体0，最终9/70成功；67次新晶体与上一轮token完全相同。切换恢复已验证，结构修正能力仍未得到改善。详见[完整结果](RESULTS.md)。
